# Переезд на VPS + Clerk

Рабочий runbook. Порядок шагов важен — особенно в разделе «Перенос салона
с Railway», где неверная последовательность стоит пересканирования QR.

## Что меняется и зачем

**Было:** один салон = один Railway-проект со своим платным Postgres.
Каждый новый салон — новый счёт.

**Стало:** один VPS, один Postgres, по контейнеру на салон. Новый салон =
новая БД на том же Postgres + контейнер. Маржинальная стоимость салона — ноль.
При подписке 500–1000 сом это и есть разница между «работает» и «в минус».

Схему БД это не трогает: изоляция идёт по контейнеру и по базе, а не по
`salon_id`. Большой рефакторинг из Фазы 2 `MULTI_SALON_PLAN.md` не нужен, и
изоляция получается строже — владелец салона физически не дотянется до чужой
БД, даже подделав фронт.

**Авторизация:** свой пароль + подписанная cookie заменены на Clerk.
Появляется роль system-admin, которая ходит между всеми салонами и
подключает им QR прямо из панели.

```
                      admin.<домен>
                           │
                    ┌──────┴──────┐
                    │    nginx    │
                    └──┬───────┬──┘
           /  и /admin/│       │/s/<slug>/
        (статика панели)       │
                               ├── salon-aruuke:3000 ──┐
                               └── salon-astra:3000  ──┤
                                                      ▼
                                              postgres (одна БД на салон)
```

Один origin на всё — CORS не нужен.

## Фаза 0 — что нужно до старта

| Что | Зачем |
|---|---|
| Домен + поддомен `admin.<домен>` | TLS обязателен: в панели логин, а PWA (`public/sw.js`) без HTTPS не работает |
| VPS куплен, есть root по SSH | — |
| Clerk-аккаунт | Авторизация панели |

Про 24 месяца предоплатой ($112.56): это лок на два года при двух клиентах.
Помесячно дороже за месяц, но если не пойдёт — потеря меньше. Решение ваше.

## Фаза 1 — Clerk

Приложение уже заведено: **`app_3JOizdai7VlphsPe0fMtOdvu9Jc`** (подставляйте
вместо `<app_id>` ниже). Ключ `pk_...` публичный, `sk_...` — секрет, в git ни
один из них не коммитим.

Инструмент: `npm i -g clerk`, затем `clerk auth login` (открывает браузер).
Без логина любая команда `clerk` ответит `auth_required`.

0. **Dev или prod.** Всё, что сделано до сих пор, — на **dev**-инстансе: он
   работает с любого адреса, включая localhost, и годится для проверки.
   Боевой инстанс — отдельная сущность со **своими ключами**, и он требует
   DNS-записей на вашем домене (Clerk выдаст набор CNAME вида
   `clerk.<домен>`, `accounts.<домен>`). Заводится так:
   ```sh
   clerk deploy --app app_3JOizdai7VlphsPe0fMtOdvu9Jc
   ```
   Дальше добавить выданные CNAME у регистратора и дождаться проверки.
   **Все настройки ниже (claims, sign-up mode) задаются на инстанс и на
   проде их надо повторить с `--instance prod`.** Права пользователей
   (public metadata) тоже не переезжают — учётки на dev и prod разные.

   Закладывайте на это отдельный день: DNS распространяется не мгновенно.

1. Метод входа — Email + пароль (для владельцев салонов это понятнее, чем
   OAuth).
2. Прокинуть `public_metadata` в session token — **без этого шага `metadata`
   не попадёт в JWT и бэкенд не пустит никого**, включая вас. Через CLI
   (`npm i -g clerk`, затем `clerk auth login`):
   ```sh
   clerk config patch --app <app_id> \
     --json '{"session":{"claims":{"metadata":"{{user.public_metadata}}"}}}'
   ```
   Добавьте `--instance prod`, когда будете заводить боевой инстанс:
   настройка задаётся на инстанс, и на проде её придётся повторить.
   То же самое руками — Dashboard → Sessions → Customize session token.

   Проверить, что доехало: выпустить токен и посмотреть claim `metadata`
   (`clerk api /sessions/<id>/tokens -X POST -d '{}'`).
3. Регистрация оставлена **открытой** (`sign_up_mode: public`) осознанно:
   человек заводит аккаунт сам, а доступ вы раздаёте в панели. Зарегаться
   может кто угодно, но без назначенного салона он видит только «Нет
   доступа» — данных за этим экраном нет.

   Если понадобится закрыть и пускать строго по приглашениям:
   ```sh
   clerk config patch --app <app_id> \
     --json '{"auth_access_control":{"sign_up_mode":"restricted"}}'
   ```

4. Завести себя как system-admin и выдать права. Права живут в **public
   metadata** пользователя:
   - system-admin (вы): `{ "role": "system_admin" }` — ходит во все салоны
   - владелец салона: `{ "salons": ["aruuke"] }` — только в свой, и **без
     доступа к QR**

   Дальше всё делается **из панели**, раздел «Доступы» (виден только
   system-admin), двумя путями:
   - **пригласить заранее** — почта + салон, письмо уходит человеку, права
     применяются при регистрации;
   - **раздать уже зарегистрировавшемуся** — в списке пользователей у
     каждого выпадашка: салон, «Системный администратор» или «Без доступа».

   Снятие доступа вступает в силу в пределах минуты (токен Clerk живёт
   60 секунд). Свои собственные права через панель поменять нельзя — иначе
   можно закрыть себе вход.

   То же самое из командной строки, если панель ещё не поднята:
   ```sh
   clerk api /invitations --app <app_id> -X POST \
     -d '{"email_address":"owner@salon.kg","public_metadata":{"salons":["aruuke"]}}'
   ```
   **Первый system-admin — курица и яйцо: панель выдать права себе не даёт,
   а до неё вы никто.** Поэтому вручную, в три шага:
   1. Зарегистрироваться обычным Sign up на странице входа. Панель покажет
      «Нет доступа» — так и надо, прав ещё нет.
   2. Найти свой `user_id`:
      ```sh
      clerk api "/users?order_by=-created_at&limit=5" --app <app_id>
      ```
   3. Выдать себе роль:
      ```sh
      clerk api /users/<user_id>/metadata --app <app_id> -X PATCH \
        -d '{"public_metadata":{"role":"system_admin"}}'
      ```
   Обновить страницу — появятся салоны. Дальше всё через панель.
   Слаг обязан совпадать с `SALON_SLUG` в env салона, локацией `/s/<slug>/`
   в nginx и записью в `public/config.json`.
5. Забрать `Publishable key` (`pk_...`, публичный, идёт во фронт) и
   `Secret key` (`sk_...`, в env контейнеров).

## Фаза 2 — VPS

1. Пользователь не-root, SSH по ключу, `PasswordAuthentication no`.
2. `ufw allow OpenSSH`, `ufw allow 80`, `ufw allow 443`, `ufw enable`.
   Postgres наружу не открывается — в `docker-compose.yml` у него намеренно
   нет `ports:`.
3. **Swap 2 ГБ** — на 2 ГБ RAM без свопа OOM-killer прибьёт контейнер:
   ```sh
   fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
   echo '/swapfile none swap sw 0 0' >> /etc/fstab
   sysctl -w vm.swappiness=10 && echo 'vm.swappiness=10' >> /etc/sysctl.d/99-swap.conf
   ```
4. Docker + compose, `systemctl enable docker`. Контейнеры подняты с
   `restart: unless-stopped` — после ребута сокеты Baileys переподнимутся
   сами из сессий в Postgres.
5. Deploy-key для приватного репо, `git clone` в `/opt/salon-bot`.

## Фаза 3 — стек

1. `.env` в корне стека — только `PG_ROOT_PASSWORD=<длинный пароль>`.
2. `public/config.json` из `public/config.example.json`: publishable key и
   список салонов.
3. `nginx/admin.conf` — заменить `ADMIN_DOMAIN` на реальный поддомен
   (встречается 4 раза).
4. Сертификат (сначала nginx поднимается на 80, чтобы отдать ACME-челлендж):
   ```sh
   docker compose up -d nginx
   docker compose run --rm certbot certonly --webroot -w /var/www/certbot -d admin.<домен>
   docker compose restart nginx
   ```
5. `chmod 600 env/*.env` — там секреты Clerk и пароли БД. В git они не
   попадают (`env/` в `.gitignore`).

## Фаза 4 — перенос салона с Railway

**Сессия WhatsApp лежит в Postgres (`wa_auth`, см. `src/waAuth.js`), поэтому
при правильном порядке QR пересканировать не нужно.** Но два процесса на
одной сессии одновременно работать не могут — они выбьют друг друга, и тогда
привязку придётся делать заново, а WhatsApp режет частые попытки.

1. Снять дамп с Railway:
   ```sh
   pg_dump "$RAILWAY_DATABASE_URL" -Fc -f aruuke.dump
   ```
2. Развернуть салон обычным способом:
   ```sh
   scripts/new-salon.sh aruuke "Aruuke" 996XXXXXXXXX
   ```
   Контейнер поднимется с пустой сессией и нарисует QR — **не сканируйте**,
   сессию сейчас заменит дамп.
3. Остановить контейнер, чтобы он не держал базу во время восстановления:
   ```sh
   docker compose stop salon-aruuke
   ```
4. Восстановить дамп. `--clean --if-exists` обязателен: `db.init()` уже
   создал пустую схему на шаге 2, и без него `pg_restore` споткнётся о
   существующие таблицы.
   ```sh
   docker compose exec -T postgres pg_restore -U postgres -d salon_aruuke \
     --clean --if-exists --no-owner < aruuke.dump
   ```
5. Проверить, что сессия приехала — должна быть строка `creds`:
   ```sh
   docker compose exec -T postgres psql -U postgres -d salon_aruuke -c "select id from wa_auth where id='creds'"
   ```
6. **Погасить сервис на Railway.** Не «задеплоить рядом» — сначала выключить.
7. Только теперь поднять контейнер обратно:
   ```sh
   docker compose up -d salon-aruuke
   ```
8. Проверка: панель → WhatsApp → статус «Подключён» (не QR). Затем живой
   тест — написать боту с телефона, дойти до подтверждения записи.
9. Railway-проект не удалять неделю. Это откат.

## Фаза 5 — бэкапы (до того как пустили клиентов)

Потеря `wa_auth` = все салоны сканируют QR заново. Это дороже, чем звучит.

```sh
cp scripts/backup.sh /opt/salon-bot/scripts/
crontab -e   # 15 3 * * * /opt/salon-bot/scripts/backup.sh >> /var/log/salon-backup.log 2>&1
```

Настроить в скрипте выгрузку за пределы машины (закомментированная строка
`rclone`). **Бэкап, который лежит только на защищаемой машине — не бэкап.**
Один раз руками проверить восстановление на тестовую БД; непроверенный
бэкап не считается.

## Новый салон

```sh
scripts/new-salon.sh <slug> "<Название салона>" [номер_админа]
```

Делает всё: базу с ролью и случайным паролем, `env/<slug>.env`, сервис в
`docker-compose.yml`, локацию в `nginx/admin.conf`, запись в
`public/config.json`, поднимает контейнер и перечитывает nginx. Схема БД не
трогается — `db.init()` накатит её сам при первом старте.

Если слаг уже занят в любом из этих мест, скрипт откажется работать целиком,
а не применит половину.

Дальше руками, через панель:
1. Выбрать салон → **WhatsApp** → отсканировать QR
2. **Доступы** → пригласить владельца на этот салон
3. Завести услуги, мастеров и часы работы
4. Завести в DeepSeek отдельный ключ, **назвать его слагом салона**, и
   вписать в `env/<slug>.env` как `DEEPSEEK_API_KEY`. Кабинет DeepSeek
   фильтрует расход по ключу и по дням — это и есть разбивка стоимости ИИ
   по салонам, своего учёта мы не ведём.

Вставка держится на якорях `# >>> salons >>>` в `docker-compose.yml` и
`nginx/admin.conf` — не удаляйте их.

## Отключить салон

```sh
scripts/remove-salon.sh <slug>              # база остаётся
scripts/remove-salon.sh <slug> --drop-db    # база удаляется насовсем
```

Спрашивает подтверждение слагом, а с `--drop-db` — ещё раз словом `DROP`.
Дамп снимается **до** любых действий и в обоих случаях; если дамп вышел
оборванным, скрипт останавливается не тронув ничего.

По умолчанию база остаётся на месте, то есть отключение обратимо: тот же
`new-salon.sh` с тем же слагом поднимет салон обратно вместе со всеми
записями и сессией WhatsApp. `env/<slug>.env` не удаляется, а переименуется
в `.removed`.

Доступы владельца в Clerk скрипт не трогает — снимите их в панели.

## Деплой кода

Замена `railway up`:

На VPS:
```sh
cd /opt/salon-bot && git pull && docker build -t salon-bot:latest . && docker compose up -d
```

Локально перед этим — пуш в **оба** remote'а, они под разными аккаунтами
GitHub, и пуш не из-под того аккаунта падает с «Repository not found»
(репозиторий приватный, потому 404 вместо 403):
```sh
gh auth switch --hostname github.com --user TimQshy  && git push origin main
gh auth switch --hostname github.com --user tima-kho && git push tima-kho main
```
`tima-kho` — рабочий аккаунт по умолчанию, оставляйте активным его.

## Мониторинг

Упавший сокет Baileys молчит — узнаете от салона. Минимум: внешний пингер на
`https://admin.<домен>/s/<slug>/` (отдаёт `OK`). Дальше можно завести
`/health`, который отдаёт 500 при `status !== 'open'`.

## Бюджет памяти (2 ГБ)

Замерено на живых процессах: бот вхолостую (сокет поднят, номер не привязан)
занимает **66–88 МБ**. С привязанным номером выше — Baileys держит в памяти
криптосессии на каждого собеседника; закладывайте 120–180 МБ.

| Компонент | RAM |
|---|---|
| ОС + docker | ~280 МБ |
| Postgres | ~150 МБ + ~7 МБ на соединение |
| nginx + certbot | ~25 МБ |
| Контейнер салона | 120–180 МБ |

**Потолок — 6–8 салонов**, дальше тариф с 4 ГБ (это дешевле рефакторинга
Фазы 2). `mem_limit: 400m` не даёт одному салону уронить остальные.

Упрётесь в память, а не в нагрузку: 100 сообщений в день на салон — меньше
одного в минуту даже при десяти салонах, одному vCPU этого не заметить.

Два места, которые аукнутся не сразу (не сделано, на будущее):
- `sessions` (`src/session.js`) и `lastMenus` (`src/menu.js`) выселяют записи
  только при обращении — кто написал раз и не вернулся, висит вечно. Около
  4 МБ в год на салон. Чистку просится повесить на крон в `src/scheduler.js`.
- Пул Postgres в `src/database.js` без `max` — дефолт 10 соединений на салон,
  при 10 салонах это ровно `max_connections`. Одна строка `max: 5` снимает
  вопрос.
