## Задача: сделать архитектуру готовой под несколько салонов

Сейчас вся система — **один салон = один деплой**. Жёстко зашито в код:

- `ADMIN_PHONES`, `ADMIN_PASSWORD`, `TIMEZONE`, `WAITLIST_OFFER_TIMEOUT_MIN` — env-переменные на процесс, не на салон
- `masters`, `services`, `working_hours`, `appointments`, `waitlist`, `messages` — таблицы без понятия "чей это салон"
- `wa_auth` — одна WhatsApp-сессия на процесс (`src/whatsapp.js` держит один глобальный `sock`)
- Админка (`/admin`) — один пароль на всех, без привязки к салону
- `db.init()` в `bot.js` — один процесс, один `DATABASE_URL`

Два пути это исправить — они не взаимоисключающие, это стадии роста.

---

### Фаза 1 — "под копирку" (готово хоть сейчас, 2–5 салонов)

Каждый новый салон = отдельный Railway-проект (свой Postgres, свой сервис
`bot`, свой `DATABASE_URL`, свой номер WhatsApp) из того же кода. Ничего
не переписывать — только повторить процесс деплоя из `IMPLEMENTATION_PLAN.md`.

**Чек-лист на новый салон:**
1. Новый Railway-проект + Postgres-плагин
2. Скопировать env из `.env.example`, заполнить под салон (`ADMIN_PASSWORD`,
   `ADMIN_COOKIE_SECRET`, `ADMIN_PHONES`, `TIMEZONE`, опционально
   `GEMINI_API_KEY`/`DEEPSEEK_API_KEY`, `WAITLIST_OFFER_TIMEOUT_MIN`)
3. `railway up --service bot` из этого же репо
4. `db.init()` сам накатит схему на пустую БД
5. Зайти на `/admin` → добавить услуги/мастеров/часы работы через панель
   (или `npm run seed` с адаптированными данными)
6. `/admin/wa-qr` → привязать номер WhatsApp этого салона

**Минус:** N салонов = N мест, куда катить один и тот же баг-фикс вручную.
При 2–5 салонах это терпимо; дальше — больно.

**Когда переходить в Фазу 2:** когда ручной деплой в N мест на каждый фикс
станет заметной тратой времени (ориентир — 5+ салонов), или когда салону
понадобится вход в свою админку без доступа к чужим данным на одном сервере.

---

### Фаза 2 — настоящий multi-tenant (один деплой, много салонов)

Нужно, когда Фаза 1 упрётся в масштаб. Основные изменения:

**1. Схема БД — добавить `salon_id` везде**
```sql
CREATE TABLE salons (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  slug TEXT UNIQUE NOT NULL,        -- для /admin/<slug>
  admin_password_hash TEXT NOT NULL,
  admin_cookie_secret TEXT NOT NULL,
  admin_phones TEXT[],
  timezone TEXT NOT NULL DEFAULT 'Europe/Moscow',
  waitlist_offer_timeout_min INT NOT NULL DEFAULT 30,
  gemini_api_key TEXT,
  deepseek_api_key TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```
Добавить `salon_id INTEGER REFERENCES salons(id)` в `masters`, `services`,
`working_hours`, `appointments`, `waitlist`, `messages`, `wa_auth` — и
переиндексировать (`idx_appt_date` → `(salon_id, appointment_date)` и т.п.,
иначе один салон будет сканировать данные другого при каждом запросе).

Все `db.*` функции в `database.js` (сейчас ~30 штук) принимают `salonId`
первым параметром. Это самая объёмная механическая часть работы.

**2. Одна WhatsApp-сессия на салон, не на процесс**
`src/whatsapp.js` сейчас — модуль с глобальными `sock`/`connectionStatus`.
Переделать в фабрику/класс: `Map<salonId, { sock, status, qr }>`,
`connectWhatsApp(salonId, onIncoming)` поднимает сокет для конкретного
салона, `sendText(salonId, to, text)` шлёт через нужный сокет. При старте
`bot.js` — цикл по всем `salons` из БД, поднять сокет на каждый.

Важно: incoming-обработчик (`handleIncoming` в `webhook.js`) должен знать,
**от имени какого салона** пришло сообщение — это определяется тем, на
какой сокет (= на какой номер) написал клиент, не самим текстом. Значит
`connectWhatsApp` должен прокидывать `salonId` в `onIncoming(salonId, phone, {...})`,
и весь дальнейший стек (`session.js`, `menu.js`, `booking.js`) — ключевать
внутреннее состояние по `${salonId}:${phone}`, не только по `phone` (два
разных салона могут обслуживать один и тот же номер клиента).

**3. Админка — per-salon авторизация и роутинг**
- `/admin/:slug/login`, `/admin/:slug/*` — `requireAuth` проверяет cookie
  привязанный к конкретному `salonId`, не общий пароль
- `adminAuth.js` — пароль хранить хешированным (`bcrypt`/`scrypt`) в
  `salons.admin_password_hash`, не голым env-значением как сейчас
- `public/admin-dashboard.html` — все `fetch('/api/...')` менять на
  `fetch('/admin/${slug}/api/...')`, или передавать `salonId` через сессию
  сервера (проще для фронта — не трогать HTML вообще)

**4. Suпер-админка (опционально, но пригодится быстро)**
Отдельная защищённая страница/скрипт для создания нового салона (вставить
строку в `salons`, сразу получить `/admin/<slug>/wa-qr`) — иначе каждое
подключение нового салона будет требовать ручного `INSERT INTO salons`.
