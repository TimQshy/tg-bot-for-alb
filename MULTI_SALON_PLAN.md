## Задача: сделать архитектуру готовой под несколько салонов

Исходная постановка (актуальна как описание кода — **один процесс = один
салон**; изменилось не это, а то, сколько стоит поднять такой процесс):

- `ADMIN_PHONES`, `TIMEZONE`, `WAITLIST_OFFER_TIMEOUT_MIN` — env-переменные на процесс, не на салон
- `masters`, `services`, `working_hours`, `appointments`, `waitlist`, `messages` — таблицы без понятия "чей это салон"
- `wa_auth` — одна WhatsApp-сессия на процесс (`src/whatsapp.js` держит один глобальный `sock`)
- `db.init()` в `bot.js` — один процесс, один `DATABASE_URL`

Фаза 1 не убирает эти ограничения, а делает их дешёвыми: процесс на салон
стоит ноль. Фаза 2 убирает их по-настоящему — и нужна только тогда, когда
упрёмся в потолок памяти или понадобится сводная отчётность.

---

### Фаза 1 — "под копирку" (сделано 2026-09-16, актуальная архитектура)

Каждый салон = свой контейнер со своей БД на одном VPS. Чеклист подключения
и весь деплой — в `VPS_MIGRATION_PLAN.md`.

Изначально Фаза 1 предполагала отдельный Railway-проект на салон, но там
каждый салон приносил отдельный счёт за Postgres — при подписке 500–1000 сом
это не сходилось. На VPS маржинальная стоимость салона нулевая.

**Что это дало против исходного плана:**
- Общий Postgres, отдельная БД на салон — изоляция данных без `salon_id`
- Один деплой катится во все салоны сразу (`docker compose up -d`), пункт
  «N мест для одного багфикса» отпал
- Админка одна на всех, вход через Clerk (см. ниже) — салону не нужен
  отдельный адрес, а system-admin ходит между салонами

**Когда переходить в Фазу 2:** когда 2 ГБ RAM упрутся в потолок (ориентир —
5–6 салонов; тогда сначала апгрейд плана VPS, это дешевле рефакторинга), или
когда понадобится общая отчётность по всем салонам сразу — её через
раздельные БД не собрать.

### Фаза 2 — настоящий multi-tenant (один деплой, много салонов)

Нужно, когда Фаза 1 упрётся в масштаб. Основные изменения:

**1. Схема БД — добавить `salon_id` везде**
```sql
CREATE TABLE salons (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  slug TEXT UNIQUE NOT NULL,        -- для /admin/<slug>
  admin_password_hash TEXT NOT NULL,
  admin_cookie_secret TEXT NOT NULL,
  admin_phones TEXT[],
  timezone TEXT NOT NULL DEFAULT 'Europe/Moscow',
  waitlist_offer_timeout_min INT NOT NULL DEFAULT 30,
  deepseek_api_key TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```
Добавить `salon_id INTEGER REFERENCES salons(id)` в `masters`, `services`,
`working_hours`, `appointments`, `waitlist`, `messages`, `wa_auth` — и
переиндексировать (`idx_appt_date` → `(salon_id, appointment_date)` и т.п.,
иначе один салон будет сканировать данные другого при каждом запросе).

Все `db.*` функции в `database.js` (сейчас ~30 штук) принимают `salonId`
первым параметром. Это самая объёмная механическая часть работы.

**2. Одна WhatsApp-сессия на салон, не на процесс**
`src/whatsapp.js` сейчас — модуль с глобальными `sock`/`connectionStatus`.
Переделать в фабрику/класс: `Map<salonId, { sock, status, qr }>`,
`connectWhatsApp(salonId, onIncoming)` поднимает сокет для конкретного
салона, `sendText(salonId, to, text)` шлёт через нужный сокет. При старте
`bot.js` — цикл по всем `salons` из БД, поднять сокет на каждый.

Важно: incoming-обработчик (`handleIncoming` в `webhook.js`) должен знать,
**от имени какого салона** пришло сообщение — это определяется тем, на
какой сокет (= на какой номер) написал клиент, не самим текстом. Значит
`connectWhatsApp` должен прокидывать `salonId` в `onIncoming(salonId, phone, {...})`,
и весь дальнейший стек (`session.js`, `menu.js`, `booking.js`) — ключевать
внутреннее состояние по `${salonId}:${phone}`, не только по `phone` (два
разных салона могут обслуживать один и тот же номер клиента).

**3. Админка — per-salon авторизация и роутинг** — ✅ сделано в Фазе 1,
отдельно от остальной Фазы 2.

Решено через Clerk, без `salons.admin_password_hash` и без bcrypt: права
лежат в public metadata пользователя (`role: system_admin` либо
`salons: [...]`), каждый контейнер сверяет их со своим `SALON_SLUG`
(`src/adminAuth.js`). Роутинг — nginx проксирует `/s/<slug>/` в нужный
контейнер, фронт ходит через один `api()` helper. Детали — в
`VPS_MIGRATION_PLAN.md`.

**4. Суперадминка** — ✅ закрыто там же. System-admin переключает салоны
выпадашкой в шапке и подключает им QR прямо из панели, отдельная страница не
понадобилась.
