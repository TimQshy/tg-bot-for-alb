## Эпик A: ИИ-консультант

### Идея (от пользователя)
- Основная модель — Gemini Flash, бесплатный tier.
- Как только приходит rate-limit callback от Gemini — fallback на DeepSeek ("костыль").
- Нужен расчёт расхода на всё.

### Архитектура

Новый модуль `src/ai.js`:
```
askAI(phone, userText, context) -> string
```
- `context` = снапшот из БД: активные услуги (`getActiveServices`), мастера, что каждый мастер делает (`master_services`), рабочие часы. Формируется в system prompt, чтобы ИИ не придумывал цены/услуги.
- Провайдер-абстракция: `callGemini(prompt)` и `callDeepSeek(prompt)` за одним интерфейсом.
- Логика fallback:
  1. Вызов Gemini Flash.
  2. Если ответ = 429 (rate limit) или явный quota-error → сразу retry на DeepSeek, без ретраев на Gemini (бесплатный tier не восстановится за секунды).
  3. Опционально: кэш "Gemini исчерпан до полуночи UTC" в памяти процесса, чтобы не бить лишний раз по Gemini весь остаток дня после первого 429 (экономия latency, не денег — но всё равно 1 лишний запрос).
- Интеграция в `webhook.js`: строка 100-104, где сейчас "используйте кнопки" — если сессии нет (не в процессе букинга) и текст не похож на команду, отправлять в `askAI`. Если пользователь в процессе букинга (`session` есть) — ИИ не трогаем, только nudge к кнопкам (иначе конфликт с flow).

### Расчёт расхода (принято: только FAQ по салону, ~50 сообщений/день, DeepSeek через официальный API deepseek.com)

- Gemini Flash free tier (Google AI Studio, ориентировочно ~1500 запросов/день, ~15/мин — **сверить актуальные лимиты на момент подключения**, Google их меняет): 50/день ≈ 3% дневного лимита. DeepSeek почти не задействуется, кроме случайных всплесков (несколько сообщений в одну минуту).
- Худший случай (гипотетически весь трафик в DeepSeek): system prompt (услуги/мастера/часы, только FAQ-скоуп) ~800 токенов + вопрос ~30 + ответ ~150 ≈ 980 токенов/диалог.
  - Месяц: 30 × 50 = 1500 диалогов → ≈1.25M input токенов, ≈0.22M output.
  - DeepSeek-chat (ориентировочно $0.14/1M input, $0.28/1M output — **сверить актуальную цену**, у DeepSeek бывают off-peak скидки): **≈ $0.24/месяц** в худшем случае.
- Вывод: при этом объёме расход несущественный. DeepSeek тут не про экономию — про надёжность на пиках. Пересчитать при росте объёма в 10+ раз.

### Решения (закрыто)
1. **Без истории диалога** — каждый вопрос independent-запрос с system prompt. Проще, дешевле, для чистого FAQ-скоупа follow-up почти не нужен.
2. **Без лимита на пользователя пока** — объём маленький (~50/день суммарно), риск абьюза низкий. Добавить лимит позже, если понадобится (задача осталась в breakdown ниже, но не блокер для MVP).
3. **Fallback при отказе обоих провайдеров** — статичное сообщение + кнопки главного меню (тот же паттерн, что уже есть в `webhook.js` для нераспознанного текста). Без уведомления админа на этом этапе.

### Задачи (черновой breakdown)
- [x] `src/ai.js`: провайдеры Gemini/DeepSeek + единый интерфейс, без хранения истории (каждый вызов — новый independent-запрос)
- [x] Формирование контекста из БД (услуги/мастера/часы) в system prompt — только FAQ-скоуп
- [x] Детект rate-limit ответа Gemini (429/quota) → fallback DeepSeek
- [x] Fallback на случай отказа обоих провайдеров → статичное сообщение + `sendMainMenu`
- [x] Врезка в `webhook.js` (свободный текст без сессии)
- [x] ENV: `GEMINI_API_KEY`, `DEEPSEEK_API_KEY` в `.env.example`
- [x] Логирование использования (`console.log` в `webhook.js` при каждом AI-ответе, с указанием модели)
- [ ] *(не блокер MVP)* Лимит запросов на пользователя/день — добавить, если объём вырастет

**Написано:** `src/ai.js`. Проверить `GEMINI_MODEL` в коде (`gemini-2.0-flash`) на актуальность у Google перед первым реальным запуском, и вписать реальные `GEMINI_API_KEY`/`DEEPSEEK_API_KEY` в `.env` (пока не задеплоено — оба провайдера пропускаются, если ключей нет).

## Эпик C: Waitlist

### Логика (от пользователя)
Если кто-то отменяет запись — предложить слот людям из листа ожидания, автоматически.

### Схема (черновая)
Новая таблица:
```sql
CREATE TABLE waitlist (
  id SERIAL PRIMARY KEY,
  user_id TEXT REFERENCES users(id),
  master_id INTEGER REFERENCES masters(id),
  service_id INTEGER REFERENCES services(id),
  desired_date DATE NOT NULL,
  status TEXT NOT NULL DEFAULT 'waiting' CHECK (status IN ('waiting','offered','booked','expired','cancelled')),
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

### Флоу
1. Слот занят при бронировании → предложить "встать в лист ожидания на эту дату/мастера".
2. Отмена записи (`confirmCancelAppt` в `booking.js`, `handleAdminCancel`, `admin.js /api/appointments/:id/cancel`) → после отмены проверить waitlist по (master_id, date) в порядке FIFO → отправить освободившийся слот первому в очереди.
3. Нужен таймаут на ответ (например 15 минут), иначе следующий по очереди.

### Решения
1. **FIFO, одному человеку за раз** — предлагаем первому в очереди, ждём ответа, не отвечает — идём к следующему.
2. **Таймаут ответа — открытый вопрос**, ждёт встречи с клиентом (заказчиком) 2026-09-14. Пока в коде сделать таймаут конфигурируемым (ENV/константа), чтобы поменять без переписывания логики, когда цифра появится.

### Задачи (черновой breakdown)
- [x] Таблица `waitlist` + функции в `database.js`
- [x] UI-ветка в `booking.js`: "слот занят" → предложить waitlist (при `chooseDate`, если на дату нет слотов)
- [x] Хук на отмену записи (3 места: `booking.confirmCancelAppt`, `booking.handleAdminCancel`, `admin.js` cancel/reschedule routes) → `waitlist.notifyNext(masterId, date)`
- [x] FIFO-логика: предложение первому, при неответе/отказе — следующему (`src/waitlist.js`)
- [x] Таймаут просрочки предложения — конфигурируемое значение (ENV `WAITLIST_OFFER_TIMEOUT_MIN`, дефолт 30 мин), **само число подтвердить после встречи с клиентом 2026-09-14**
- [x] Scheduler для таймаута — см. эпик D (`src/scheduler.js`)

**Написано:** `src/waitlist.js` (join/notifyNext/offer-confirm/offer-decline/expire), схема в `database.js`, хуки в `booking.js` и `admin.js`. Не проверено вживую на реальной БД — стоит прогнать сценарий (бронь → нет слотов → waitlist → отмена другой записи → предложение → подтверждение) на dev-окружении перед продом.

## Эпик D: Флоу букинг-менеджмента и автоматизация

Пересекается с C (waitlist нужен scheduler). Также: старый `reminders.js` (Telegram) снесён — для WhatsApp напоминаний ещё нет.

### Решения
1. **Scheduler: `node-cron` внутри процесса** — тикает раз в N минут, проверяет БД (`appointments` на приближающиеся даты, `waitlist` на просроченные предложения). Раз состояние живёт в БД (не в памяти) — рестарт процесса между тиками не теряет задачи, просто следующий тик их подхватит.
2. **Два напоминания: за 24ч и за 2ч** до записи.

### ⚠️ Блокер по напоминаниям — WhatsApp 24-часовое окно
Cloud API не даёт слать произвольный текст, если клиент не писал последние 24ч — нужен заранее одобренный Meta **message template**. Запись обычно бронируется за дни вперёд, так что оба напоминания почти наверняка попадут вне окна переписки. Значит нужны:
- Approved-шаблон "напоминание за 24ч" и отдельный "напоминание за 2ч" (или один параметризованный шаблон на оба случая) — подать на модерацию в Meta Business Manager заранее, апрув может занять время.

### Задачи (черновой breakdown, обсудим детальнее отдельно)
- [ ] **Подать 1-2 message template'а в Meta Business Manager на модерацию** (напоминание за 24ч/2ч) — это ручное действие в кабинете Meta, я это сделать не могу; сделать пораньше, апрув не мгновенный. Пока код шлёт обычный `sendText` — сработает только если клиент писал боту в последние 24ч
- [x] `node-cron` job: раз в 5 минут сканирует `appointments` на "через 24ч"/"через 2ч" и шлёт напоминание (помечает `reminder_24h_sent`/`reminder_2h_sent`, чтобы не дублировать)
- [x] Тот же cron обрабатывает просроченные waitlist-предложения (таймаут из эпика C) → следующий в очереди
- [ ] No-show обработка (отметить статус, освободить слот, триггернуть waitlist) — не сделано в этом заходе
- [x] Уведомление админам о новой записи — уже было в `booking.confirm()` (`ADMIN_PHONES`), плюс добавил такое же уведомление при записи из waitlist

**Написано:** `src/scheduler.js`, `node-cron` подключён в `bot.js`. Реальная отправка напоминаний упирается в approved-шаблон Meta — без него сообщения за пределами 24-часового окна просто не дойдут.

## Эпик E: Анализ истории чатов → план автоответов (FAQ)

### Идея (от пользователя)
"Веб-скрейпер", просматривающий все чаты WhatsApp, чтобы составить план автоответов на часто задаваемые вопросы.

### Важно — способ сбора данных
Браузерный скрейпинг WhatsApp Web (логин под номером салона + чтение DOM чатов) нарушает ToS WhatsApp, риск блокировки номера. Не делаем. Вместо этого — логирование через сам бот: раз всё и так идёт через `webhook.js`, просто писать входящие/исходящие сообщения в новую таблицу `messages`.

### Решения
1. **Без старой переписки** — старого WhatsApp-архива до бота нет/не нужен, работаем только с тем, что накопит сам бот. Значит для анализа сперва нужно набрать какой-то объём (пока трафик мал — ~50/день — реального прогона можно ждать несколько недель, чтобы набрать статистику).
2. **Разовый прогон**, не периодический процесс. Скрипт запускается вручную, когда накопится достаточно данных.
3. **Утверждение — сам, вне админки.** Скрипт просто выводит черновой список `{вопрос-паттерн → предлагаемый ответ}` (в файл/консоль), сам просматриваешь и правишь руками. Без UI в админке.

### Флоу
1. `messages` таблица: `id, phone, direction (in/out), text, created_at` — писать из `webhook.js` (входящие) и из `whatsapp.js` (исходящие).
2. Разовый скрипт `src/scripts/analyzeChats.js`: тянет накопленные `messages`, прогоняет через ИИ (тот же Gemini/DeepSeek из эпика A) с промптом "вот сообщения клиентов, выдели повторяющиеся вопросы и предложи короткие ответы".
3. Результат — черновой список в файл (например `faq-draft.json` или markdown), ты просматриваешь и правишь руками.
4. Утверждённые пары → статический конфиг (простой JSON/JS-файл, без отдельной таблицы БД — раз прогон разовый и правишь руками, таблица избыточна), который эпик A использует как приоритетные ответы до похода в LLM.

### Задачи (черновой breakdown)
- [x] Таблица `messages` + запись входящих в `webhook.js`, исходящих в `whatsapp.js` (`sendText`)
- [x] Разовый скрипт `src/scripts/analyzeChats.js`: сборка истории → прогон через LLM → черновой список FAQ в консоль (`npm run analyze-chats`)
- [ ] Ручной просмотр/правка черновика (не код, ручная работа — делать когда накопится история)
- [ ] Формат хранения утверждённых FAQ — статический конфиг-файл (напр. `src/faq.js`) — писать код, когда появится реальный черновик для правки
- [ ] Точка использования в эпике A: перед вызовом Gemini/DeepSeek сначала матчинг на `faq` (дешевле и быстрее) — тоже после появления `src/faq.js`
- [ ] Запускать `analyzeChats.js` не раньше, чем накопится содержательный объём сообщений (скрипт сам ругнётся, если сообщений <20)
